# Bookstore database schema

This document describes the schema implied by the current JPA domain model. It is the
current modular-monolith design, not a migration script. Before production data is
managed, introduce Flyway or Liquibase migrations and replace `ddl-auto` schema
generation.

## Current logical schema

```text
user_account
  1 ─── 0..1 cart
  1 ─── 0..n customer_orders

cart
  1 ─── 0..n cart_items ─── n..1 book

book
  1 ─── 1 inventory

customer_orders
  1 ─── 1..n order_items ─── n..1 book

user_account
  1 ─── 0..n checkout_idempotency
checkout_idempotency
  n..1 ─── 0..1 customer_orders
```

### Relationship summary

| Relationship | Cardinality | Meaning |
|---|---:|---|
| `book` → `inventory` | `1:1` | Every book has one stock record |
| `user_account` → `cart` | `1:0..1` | A user may have one active cart |
| `cart` → `cart_item` | `1:0..n` | A cart contains zero or more items |
| `book` → `cart_item` | `1:0..n` | A book may appear in many users' carts |
| `user_account` → `customer_orders` | `1:0..n` | A user may place many orders |
| `customer_orders` → `order_item` | `1:1..n` | An order contains one or more item snapshots |
| `user_account` → `checkout_idempotency` | `1:0..n` | A user can use many checkout keys over time |
| `checkout_idempotency` → `customer_orders` | `0..1:1` | A processing claim may have no order yet; a completed claim references one order |

The current entities store `userId` and `bookId` as UUID values rather than JPA
relationships. This keeps aggregates independent, but production migrations should add
foreign-key constraints where the ownership and delete rules are finalized.

## Tables and keys

| Table | Purpose | Primary key | Important columns and constraints |
|---|---|---|---|
| `book` | Catalogue metadata | `id` UUID | `title` and `author` required; `price >= 0`; optional `isbn` |
| `inventory` | Current stock for one book | `id` UUID | Unique, non-null `book_id`; `stock_quantity >= 0` |
| `user_account` | Authentication identity | `id` UUID | Unique, non-null `email`; `password_hash`; optional `display_name` |
| `cart` | One user's active cart | `id` UUID | Unique `user_id`, enabling one-cart ownership and efficient cart lookup |
| `cart_item` | A book and quantity in a cart | `id` UUID | `book_id`; positive `quantity` |
| `cart_items` | Current JPA collection join table | `cart_id`, `items_id` | Links `cart` to `cart_item`; generated by the current unidirectional `@OneToMany` mapping |
| `customer_orders` | Order aggregate | `id` UUID | `user_id`; `created_at`; `status` enum; `idx_customer_orders_user_created` supports order history |
| `order_item` | Immutable purchase snapshot for an order | `id` UUID | `book_id`, `book_title`, non-negative `unit_price`, positive `quantity` |
| `customer_orders_items` | Current JPA collection join table | `order_id`, `items_id` | Links `customer_orders` to `order_item`; generated by the current unidirectional mapping |
| `checkout_idempotency` | Durable duplicate-checkout protection | `id` UUID | Unique `(user_id, idempotency_key)`; request fingerprint; `PROCESSING`/`COMPLETED`; resulting `order_id` |

Inventory is intentionally separated from catalogue metadata. This avoids mixing frequently
changed stock state with relatively stable book details and gives inventory a clear boundary
for future reservations, warehouses, stock versions, and stock-ledger fields.

The current schema does not yet include payment, shipment, address, product category,
refresh-token, audit, or outbox tables. Payment interfaces exist, but no real payment
provider workflow has been implemented.

## Joins and typical queries

The catalogue uses a repository query joining inventory and filtering available stock:

```sql
SELECT b.*, i.stock_quantity
FROM book b
JOIN inventory i ON i.book_id = b.id
WHERE i.stock_quantity > 0;
```

A cart read joins through the generated collection table:

```sql
SELECT c.id, ci.book_id, ci.quantity
FROM cart c
JOIN cart_items link ON link.cart_id = c.id
JOIN cart_item ci ON ci.id = link.items_id
WHERE c.user_id = ?;
```

An order read follows the equivalent order join:

```sql
SELECT o.id, o.user_id, o.status, oi.book_id, oi.quantity
FROM customer_orders o
JOIN customer_orders_items link ON link.order_id = o.id
JOIN order_item oi ON oi.id = link.items_id
WHERE o.id = ?;
```

Idempotency lookup must use the composite unique key:

```sql
SELECT *
FROM checkout_idempotency
WHERE user_id = ? AND idempotency_key = ?;
```

## Is one database enough?

Yes. One MySQL database is sufficient for the current catalogue, cart, authentication,
idempotency, and future checkout workflow. It provides the simplest transactional
boundary for stock reservation, order creation, cart clearing, and idempotency.

Start with one primary database, connection pooling, indexes, backups, encryption in
transit/at rest, and migrations. Split databases only when ownership, scale, compliance,
or team boundaries justify the operational cost.

## Higher traffic: replicas and sharding

Use read replicas before sharding:

1. Keep writes, inventory changes, orders, carts, users, and idempotency on the primary.
2. Route safe catalogue reads to replicas after replication-lag handling is designed.
3. Keep checkout reads that require read-after-write consistency on the primary.
4. Add caching for catalogue data only after measuring database load.

Sharding is not needed now. If traffic eventually requires it, shard by a stable key such
as `user_id` for carts, orders, and idempotency records. Catalogue/inventory may need a
different strategy. Cross-shard checkout transactions are substantially harder, so keep
inventory and order data co-located where possible. Do not use sharding as a replacement
for indexes, query tuning, replicas, caching, or partitioning.

## Database and application security

- Use a separate application database user with only required CRUD permissions.
- Do not use the database root/admin account from the application.
- Store credentials in Vault or the deployment secret store.
- Use TLS for database connections in staging/production.
- Hash user passwords with a one-way adaptive password encoder.
- Never store card numbers, CVV, raw tokens, authorization headers, or plaintext passwords.
- Restrict network access to the database and disable public exposure.
- Encrypt backups and define retention/restore procedures.
- Add audit logging for authentication, stock, order, and payment events without logging secrets.
- Use migrations and schema validation; do not use `ddl-auto=update` for production.

## H2 and MySQL

### H2

The default profile uses an in-memory H2 database:

```text
jdbc:h2:mem:bookstore
```

H2 is used for local development and tests. `data.sql` seeds sample books. Data is
ephemeral and must not be used as production storage.

### MySQL

The `mysql` profile uses externally supplied host, port, database, username, and password
values. It disables H2 seed initialization and uses Hibernate schema validation:

```bash
mvn -pl backend spring-boot:run -Dspring-boot.run.profiles=mysql
```

The `vault` profile is intended for production-like deployments and obtains datasource
values through Spring Cloud Vault. MySQL is the currently supported production-ready
relational target.
